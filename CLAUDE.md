# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

SCRABBLE is a system for analyzing a Scrabble game in real time. It reads the board, the tiles on it, and each player's score, much like chess.com's live analysis during chess tournaments. The user talks to Claude in Polish, but **everything in the repository is written in English**: code, comments, on-screen text, messages, README and folder names.

**Hard rule: YOLO must not be used anywhere in this project**, in any version or form (ultralytics, darknet, etc.).

## Commands

The stack is Python 3.11 (`/usr/bin/python3.11`) + OpenCV, with a local virtualenv in `.venv`. numpy is pinned to 2.4.x because 2.5+ requires Python 3.12.

```bash
./start [annotate] [IMAGES_DIR]                      # mark board corners (default IMAGES_DIR: dataset/photos)
./start app                                          # test app in the browser (Streamlit)
./start clock [--players NAME ...] [--minutes N] [--photos DIR | --clock-only]   # clock + camera page + game preview
./start camera [SOURCE]                              # live camera view to aim it (g: grid, s: save frame)
/usr/bin/python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt   # setup
env -u PYTHONPATH .venv/bin/pytest -q                # all tests
env -u PYTHONPATH .venv/bin/pytest tests/test_annotate.py::test_save_moves_photo_and_writes_label   # single test
```

`./start` unsets `PYTHONPATH` and creates `.venv` if it is missing. It also sets `QT_QPA_PLATFORM=xcb`, because the user runs Wayland and opencv-python's bundled Qt has only the xcb plugin. It symlinks `/usr/share/fonts/truetype/dejavu` into `cv2/qt/fonts`, because that bundled Qt ships no fonts and ignores `QT_QPA_FONTDIR`. Always unset `PYTHONPATH` when running anything by hand: the user's shell exports ROS Jazzy / MoveIt paths (Python 3.12 site-packages), which leak foreign packages into the venv.

## Architecture

The current scope: the corner dataset and model, the top-down board view, tile reading (tile dataset and classifier) and scoring (`scrabble/game.py`). `scrabble/app.py` is a simple Streamlit test app (`./start app`) for checking the pipeline and the scoring by eye (Game view with per-word score breakdown, Single photo view); it is not the final frontend. Its defaults (Game view, `corners.pt`, `test_photos/gameplay/1`; each sample game is a subfolder of `test_photos/gameplay/` with one photo per move) are the constants at the top of the file; README.md describes how to use it. A game has three browser pages: the clock, the camera page and the game preview. `scrabble/clock.py` serves the first two (stdlib HTTP server + inline JS, no Streamlit, so it ticks live and takes Enter) and starts the third as a Streamlit subprocess (`start_preview`, `app.py` at `?game=live`). Enter/Space ends a turn and POSTs it to `/turn` at once (not queued, so the photo is taken at the press); `Scorer.in_order` hands out tickets so turns and resets are still scored in arrival order, asks the camera for the turn's photo when the ticket is issued, and the page drops answers older than the one shown or from before a reset. `on_turn_end` prints each turn. The `Scorer` reads the turn's photo and plays it in a `Game` for the player who pressed the clock (it sets `game.turn`, so the clock decides who made the move); the clock shows the move and the scores, and its reset POSTs `/reset`. A refused move (`Scorer.refused`, sent as `refused`) makes the page go back to the press: the next player gets back the time used while reading, the turn returns to the mover and the clock stops; S POSTs `/loss` (`Scorer.loss`, `Game.lose`: a PFS 3.2.3 loss, 0 points, turn passes on, recorded as `"loss"`), Enter ends the turn again with a new photo (a misread). The camera page (`scrabble/camera_page.py`, served at `/camera`) opens the browser's own camera (getUserMedia: a USB camera on this computer, or a phone on the same Wi-Fi; getUserMedia needs a secure context, so `main` also runs a second `make_server` on `0.0.0.0:--phone-port` (8643) wrapped by `use_https` with a self-signed cert from `certificate` (openssl, `.cert/<lan ip>.pem`, gitignored); no cloud hosting, deliberately: an https page elsewhere couldn't reach the laptop's http server), long-polls `/camera/next` for asked-for shots and POSTs full-resolution JPEGs to `/camera/photo`; `CameraPage` is the Scorer's camera (`request` / `frame`, FIFO, one shot per turn, 10 s timeout, "not open" when the page hasn't polled for 30 s). It also POSTs a 1280 px frame to `/camera/grid` about three times a second and draws the returned `corners.grid_lines` over the live view. Each game gets a folder `DIR/<timestamp>/` (`--games`, default `dataset/camera`, gitignored) made at the game's start with an empty `game.json`, removed on reset/exit if it has no photos; every turn saves the photo as the next `NNN.jpg` there and `game.save_record` rewrites `game.json` (players; per photo: who played it, whether its move was refused, a loss, or a refused move forced). With `--photos DIR` the Scorer instead reads the next unused photo in `DIR` (natural name order) and there is no camera page or preview; `--clock-only` runs the clock alone. `app.py` lists `dataset/camera/` folders too and, when a folder has `game.json` (`game.load_record`), takes the players and each photo's player and forcing from it instead of alternating turns; its "Follow the clock's game" toggle (default on with `?game=live`) shows the newest folder with a record, reruns via a `run_every` fragment when its move count changes and jumps to the newest move. `scrabble/camera.py` (`./start camera`, OpenCV window for V4L2/stream sources) is now only an aiming and dataset tool; its `Camera` reads frames in a thread so a frame is never stale. The camera is a USB camera or a phone; it is mounted above the board, maybe slightly at an angle. Only one game at a time for now; a page listing all games, each viewable separately, comes later. Photos are taken only on clock presses: continuous live tracking and the final frontend come later; don't add them unless asked.

The dataset flow, with every path under `dataset/`:
1. The user takes the photos with a phone and copies them into `photos/`, or saves camera frames there with `./start camera` (`s`).
2. `scrabble/annotate.py` is an OpenCV GUI. The user clicks the 4 outer corners of the whole printed board (coordinate strips and SCRABBLE bar included) IN ORDER: 1 is the board's top-left (the board's, not the photo's), then clockwise. Points are stored exactly in click order and never re-sorted, so they encode board orientation. Don't reintroduce automatic corner sorting. Saving is refused unless `is_clockwise_convex` holds. On save, it writes `labels/<photo stem>.json` as `{"image": "<name>", "corners": [[x, y] x4]}`, in original-resolution pixels, and then moves the photo to `annotated/`. Labels are linked to photos by file stem. Running it on `dataset/annotated` reloads the existing labels and rewrites them in place without moving anything. It refuses to overwrite a photo of the same name that is already in `annotated/`. README.md holds the user-facing instructions.
3. `scrabble/corners.py` trains a ResNet18 heatmap model (`models/corners.pt`, gitignored) that predicts the 4 grid corners (the labels' `"grid"`, see below); `predict_corners` turns them into board corners with `board.board_from_grid`, so everything downstream still works with board corners. `scrabble/board.py` maps board corners to the 15×15 cell grid with the fixed `GRID_IN_BOARD` fractions (measured on the average of all rectified labelled photos), warps the photo to a top-down grid and cuts it into cells. `board.fit_grid` then moves the grid onto the board's printed lines (per-band line peaks, then a least-squares line homography with outlier rejection), because the network's corners are only accurate to about half a cell near the edges; `predict_corners` does it by default (`fit=False` for the network alone). The hand labels are only accurate to about 0.3 cell, so they can't evaluate the fitted grid; judge it on reading results (test_photos) instead. `python -m scrabble.corners evaluate` compares corner models on the same validation photos. `python -m scrabble.check grid` re-measures `GRID_IN_BOARD`; `python -m scrabble.check labels` draws contact sheets for checking labels. We are moving from board corners to grid corners (the 15×15 cell grid's outer corners, same order), so the corner model won't depend on one board's `GRID_IN_BOARD`: `python -m scrabble.check grid-labels` adds them to every label as `"grid"` (GRID_IN_BOARD + `fit_grid`, `max_shift=1.5`) with previews in `dataset/check_grid/` (gitignored); `"corners"` stays the hand-marked board corners. The corner model trains on `"grid"`; `annotate.py` and `tiles.photo_corners` still use `"corners"`, and `annotate.py` rewrites a label without `"grid"`, so run `grid-labels` again after annotating. Models trained on board corners don't work with the current `predict_corners`.
4. `scrabble/tiles.py` draws 6 tile layouts (the whole Polish tile set in alphabetical order from a different start cell each) and cuts labelled 96×96 cell crops (64 px cell + 16 px context) from photos of them into `dataset/tiles/cells/<class>/` (gitignored, regenerable). Tile photos live in `dataset/tiles/layout_NN/{photos,annotated,labels}`, annotated with `./start dataset/tiles/layout_NN/photos --dataset dataset/tiles/layout_NN`. `scrabble/letters.py` trains a ResNet18 cell classifier (34 classes: 32 letters, `_blank`, `_empty`; `models/letters.pt`) with validation on whole held-out photos, and `predict` runs the full photo → corners → cells → letters pipeline. Current accuracy and known weaknesses are in the "Current results" section of README.md; update it after retraining.
5. `scrabble/game.py` finds the move between two read boards (new tiles in one line, no gaps, touching old tiles, the first move on the centre) and scores it: Polish tile values, premium squares only under new tiles, cross words, +50 for all 7 tiles. Words are not checked against a dictionary and a blank scores 0; both are deliberate for now, and so is the 7-tile limit per move. `Game` keeps the tiles it has accepted: a later photo that reads an old tile differently doesn't change it (reported in `misread`); new tiles not linked through neighbouring tiles to the old tiles or the centre are dropped as misreads (`drop_isolated`, reported in `ignored`; the largest group stays if the centre is empty), and `play(board, force=True)` accepts a refused move's tiles for 0 points. `Game` also counts the bag and each rack from the tiles played (7 each at the start, drawing back up while the bag lasts) and the pauses in a row (turns without new tiles; `play(..., exchange=True)` resets the count, as an exchange is not a pause; `lose()` adds a loss, and with losses in the run it takes one more round of pauses and losses, PFS 5.1.1b). The end-of-game rules are the PFS tournament rules (Regulamin Turniejów PFS 5.1, 6.2); keep them so: `Game.end()` gives `(OUT, player)` when the bag and the mover's rack are empty, `(PASSES, None)` after 2 pauses per player still playing (4 for two players; 2 for one playing on alone) and `(TIME, None)` when every player's time ran out; `time_out(player)` takes a player out of the game (no more moves, no time penalty points) and restarts the pause count. `left_value` is the points of all tiles not on the board, `final_scores` takes each rack's points off and gives a player who played out the others'. The clock: X ends a turn as an exchange (sent as `exchange`, recorded per photo in `game.json`), a player at 0:00 is POSTed to `/timeout` and skipped from then on; a result with `end` (`Scorer.end_info`, with the rack points the board determines) opens the end form, which POSTs `/end` with `left` (`Scorer.finish`) and records `"end": {reason, player, left}` in `game.json`, which `app.py` shows above the last move. Racks' letters are never known, so the rack points are typed in where they can't be derived. `python -m scrabble.game PHOTOS_DIR` scores a game from photos in the terminal.

`cv2.imread` applies the EXIF orientation of phone photos, so label coordinates refer to the rotated image. Any future loader must read photos the same way and must not use `IMREAD_IGNORE_ORIENTATION`.
